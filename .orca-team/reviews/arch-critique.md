# Architecture critique — reviewer: antigravity/Gemini 4 Neon (XHigh)

- [WINDOWS/SQLITE-TRAP] `.env.example:12` sets `DATABASE_URL=sqlite:///./data/abhas.db` and `scripts/setup.mjs:31` copies it into `.env`, overriding `apps/api/app/core/config.py:22`'s `REPO_ROOT`-anchored absolute path; because `scripts/py.mjs:19` executes Python with `cwd=apps/api`, migrations/seed/dev write to `apps/api/data/abhas.db` (failing if `apps/api/data/` does not exist) while root-run tools resolve `<repo>/data/abhas.db`. Fix: resolve relative SQLite URLs against `REPO_ROOT` in `config.py` (or comment out `DATABASE_URL` in `.env.example` so the `REPO_ROOT` default applies) and `mkdir(parents=True, exist_ok=True)` before connecting.
- [SETUP-180S-TRAP] `apps/api/pyproject.toml:15-22` bundles heavy offline/optional packages (`statsmodels`, `scikit-learn`, `openpyxl`, `anthropic`) into runtime `dependencies` exported to `requirements.txt` (179 lines), while `scripts/setup.mjs:33-47` installs Python and `apps/web` sequentially, parses the 31,320-row `.xlsx` via `openpyxl` on every clone, hardcodes Windows `py -3.12` (fails when `python` 3.12 is on `PATH` without the `py` launcher), and passes `--only-binary=:all:` which breaks if any transitive `statsmodels`/`openpyxl` dependency lacks a Windows py3.12 wheel (`NFR-5`/`AC-9`). Fix: split `statsmodels`, `scikit-learn`, `openpyxl` into a `[dependency-groups] train` group, seed from a committed normalized CSV, fall back `py -3.12` → `python`, and run Python + `npm ci` installs in parallel.
- [CONTRACT-CONFLICT] `apps/api/app/core/types.py:11-14` binds `WardId` to regex `^(DNCC|DSCC|CCC|GCC|NCC)_Ward_\d{2}$` at Pydantic validation time, so non-matching unknown wards (including `XYZ_Ward_99` in `scripts/smoke.mjs:38` and invalid `?ward=` URLs) return **422** `/validation-error` instead of **404** `/unknown-ward`, violating `PRD.md` AC-2/AC-4/AC-8. Fix: relax `WardId` schema validation to a safe non-injection character set (`^[A-Za-z0-9_-]{1,32}$`) and enforce ward existence in the repository/service layer so every unknown ward returns `404` `/unknown-ward`.
- [CONTRACT-GAP] `IsoWeek` (`app/core/types.py:28-34`) checks only `weekday() == 0` with no dataset bounds (`2016-02-29…2025-12-29`), and `ScenarioRequest.horizons` (`features/forecast/schemas.py:85`) omits the uniqueness validator present on `ForecastRequest` (`schemas.py:49-55`); Schemathesis (`gates.mjs contract`) will fuzz out-of-range Mondays (`0001-01-01`, `9999-12-27`) and duplicate horizons (`[3, 3]`) past Pydantic into services. Fix: add `ScenarioRequest` horizon deduplication in `schemas.py` and enforce explicit date-range validation (`422` `/validation-error`) in the forecast/heatmap/advisory services before any DB or cache access.
- [BOOT-CRASH/SECURITY] `.env.example:5` documents `APP_ENV=dev | test | prod`, whereas `app/core/config.py:19` requires `Literal["dev", "test", "production"]` — setting `APP_ENV=prod` crashes startup; simultaneously, neither `main.py` nor `ADR-0008` enforces an HTTP request-body size limit (`413`), allowing multi-MB JSON payloads to exhaust memory before validation (`production-standards` §2, `redteam`). Fix: align `APP_ENV` enum across `.env.example` and `config.py`, and add an ASGI 64 KB body-size limit returning `413 application/problem+json`.
- [SPOF/READINESS] `apps/api/app/main.py:25-29,56-59` hardcodes `app.state.ready = True` in `lifespan`, never pings SQLite or checks the joblib model SHA-256 in `/readyz`, returns HTTP `200` even when `"status": "starting"`, and omits `503` from `/readyz` in `contracts/openapi.json:2607`. Fix: verify artifact SHA-256 and load the model once in `lifespan`, probe SQLite (`SELECT 1` + `wards` count > 0, ≤ 2 s timeout) in `/readyz`, and return `503 application/problem+json` naming the failed dependency when unready.
- [CONCURRENCY/NFR-2] All port Protocols (`app/ports/*.py`) and stub routers are synchronous `def`, and `ADR-0005` specifies no single-flight lock around Open-Meteo refreshes; under 20 VUs (`NFR-2`), a cold live-weather cache can launch 20 duplicate Open-Meteo requests (violating `NFR-7`: ≤ 1 call/6 h) and tie up worker threads for 15–35 s, while LightGBM's default multi-threaded OpenMP runtime thrashes CPU across concurrent threadpool calls on Windows. Fix: wrap Open-Meteo refresh in a single-flight lock, pin `n_jobs=1` on serving LightGBM boosters, and replace `BaseHTTPMiddleware` (`core/logging.py`, `core/ratelimit.py`) with pure ASGI middleware to remove per-request stream overhead.
- [SLICE-BOUNDARY] `docs/architecture.md:38` places shared forecast execution for `heatmap` in `app/shared/`, and `advisory` also needs a ward's forecast + drivers, while `ADR-0001` restricts `app/shared/` to `features.py`, `tiers.py`, and `drivers.py`; without a defined shared domain service, CORE will either violate `gates.mjs slices` via cross-feature imports or duplicate forecast/cache logic across `forecast`, `heatmap`, and `advisory`. Fix: explicitly authorize one pure port-injected `app/shared/forecasting.py` (used by `forecast`, `heatmap`, and `advisory`) in `docs/architecture.md` and `ADR-0001`.
- [PORT-MISMATCH] `ForecastModel.predict(rows: Sequence[Mapping[str, float]], horizon: int)` (`app/ports/forecast_model.py:23`) accepts numeric-only feature mappings yet returns `tier` and `tier_escalated`, which `ADR-0004` defines using each ward's per-ISO-week epidemic threshold (`mean + 2 SD`) — forcing adapters to smuggle `ward_id` strings inside float dicts (breaking `pyright` and risking train/serve skew). Simpler alternative: have `ForecastModel.predict` return raw `(expected_cases, contributions)` and compute NegBin bands, `risk_score`, and `tier`/`tier_escalated` in pure `app/shared/tiers.py` using artifact calibration metadata + explicit `(ward_id, target_iso_week)`.
- [PORT-MISMATCH] `CallLog` (`app/ports/repositories.py:58-67`) exposes only `today(kind) -> (calls, spend_usd)` and `PredictionCache` exposes only `get/put/count`, lacking `calls_total`, `cache_hits`, `errors`, and `p50_ms`/`p95_ms` required by `OpsResponse` (`contracts/openapi.json:981-1065`), and `WeatherSource.weekly(city, weeks)` (`ports/weather.py:24`) is city-scoped while dataset mode has ward-distinct weather (`TASK.md:66`). Fix: extend `CallLog`/`PredictionCache` (or add an `OpsMetrics` port) with read stats and explicitly restrict `WeatherSource` to `live` mode while `dataset` mode reads ward-specific weather directly from `ObservationRepository`.
- [ML-SKEW-RISK] `ADR-0003` trains a single global LightGBM model per horizon `h = 1..4` using only `≤ origin_week` features, yet `ADR-0005` fetches `forecast_days=16` from Open-Meteo and `PRD.md` line 116 says live mode uses forecast rain for weeks after `origin_week`; feeding future rain into a model trained without future-rain columns is undefined, and training a second `h = 4` model adds complexity and calibration drift. Simpler alternative: either drop `forecast_days` from live inference (use `past_days=92` observed rain only, zero train/serve skew) or explicitly document shifting live `h = 4` to evaluate the `h = 2` model at `origin + 2w` using Open-Meteo forecast rain and benchmark its degraded-forecast error.
- [AC-7-ML-RISK] `ADR-0003:14` applies monotone-increasing constraints to "rain lags 2–4", which is ambiguous between target-relative lags and origin-relative features: in `POST /api/v1/scenario` (`AC-7`), overriding `origin_week`'s `rainfall_mm` changes `rain_lag_0`, `rolling_sum_0_3`, and `rain_anomaly`, NOT `rain_lag_2..4` (relative to `origin_week`); unconstrained splits on `rain_lag_0`/`rolling_sum_0_3`/`rain_anomaly` can still make `h = 3` predictions non-monotone. Fix: constrain `rain_lag_0`, `rolling_sum_0_3`, and `rain_anomaly` (`+1`) for horizons `h = 2..4` (or align feature naming strictly to origin-relative lags) and assert `AC-7` monotonicity across all 60 wards in unit tests.
- [OPENAPI/ERROR-SPEC] `apps/api/app/core/errors.py:53` emits `"content": {"application/problem+json": {}}` (empty schema) alongside `application/json`, `Problem` omits the `request_id` field mandated by `production-standards` §2, and `features/ops/router.py:17` aliases `401: PROBLEM_RESPONSES[404]`, documenting HTTP 401 in `contracts/openapi.json:1956` as `"Unknown ward, city or resource"`. Fix: attach `Problem`'s schema directly to `application/problem+json`, define a dedicated `401` entry for `ops`, and either add `request_id` to `Problem` or explicitly standardize on the `X-Request-ID` header.
- [RATE-LIMIT/COST-RISK] `RateLimitMiddleware` (`app/core/ratelimit.py:20`) stores an unbounded `dict[str, deque]` (memory leak under rotating client IPs in Stage 2) and applies one flat `120 req/min` limit to cheap GETs and cost-bearing `POST /api/v1/advisory`. Fix: evict stale IP entries with a bounded cache cap and apply a stricter `20 req/min` per-IP limit on `POST /api/v1/advisory` when `llm_enabled` is true.
- [MISSING-NFR/TEST-CONFIG] `ADR-0007` runs `next dev` to save setup time but specifies no security headers (`CSP`, `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy` required by `production-standards` §5) and ignores Windows first-request dev-compilation latency (Recharts + Bengali fonts) inside `NFR-5` (`≤ 180 s`); additionally, `apps/api/pyproject.toml:51` omits the `faults` pytest marker required by `system-design` (`pytest -m faults`). Fix: configure security headers in `apps/web/next.config.ts`, benchmark cold first-render on Windows in `fresh-clone`, and register `faults` in `pyproject.toml`.
